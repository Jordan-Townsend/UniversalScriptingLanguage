# PHP int64/control source translation

`semantic_php.py` implements a real PHP source frontend for the explicitly restricted profile `usl.php.int64-control.v1`. It runs the actual installed PHP `token_get_all(source, TOKEN_PARSE)` parser without executing the submitted source, obtains its real integer width/version/binary and token identity, and builds an AST using the upstream PHP Tree-sitter grammar. Accepted syntax becomes typed/effect USL IR; PHP source is not retained as an opaque executable envelope.

The current profile requires the observed 64-bit PHP host and LF `PHP_EOL`. Its values are signed int64 integers and booleans. It supports local assignment, bounded addition/subtraction/multiplication/unary signs, strict same-type comparisons, explicit Boolean control/short circuit, `intdiv`, integer remainder, canonical `echo integer, PHP_EOL`, pure typed functions with independently declared domains, and finite constant-counter `for` loops. Function names follow PHP's case-insensitive binding; local variable names remain case-sensitive. Actual installed internal function names are reserved, and special/host/superglobal variables cannot masquerade as closed local variables.

PHP integer overflow promotes arithmetic results to floating point, while Python and JavaScript BigInt can represent larger integers. The frontend therefore proves conservative result intervals remain in `[-2^63, 2^63-1]`; it refuses unproved arithmetic rather than change that behavior. Literal overflow and unary negation of `PHP_INT_MIN` reject. Function annotations must genuinely be `int`/`bool`; external input and successful-return bounds are independently supplied, every source call must remain in its declared parameter domain, and each function body must satisfy its declared successful return bounds. Recursion, captured globals, objects/references, implicit coercions, floats and libraries are outside this profile.

`validate_php_bounds(program)` independently derives bounds from the **actual IR**. It does not trust the frontend's recorded arithmetic assertions or call the main IR analyzer recursively. The main analyzer invokes it for PHP IR. Changed operations, widened calls, changed numeric/error/output policies, oversized literals/counters and violated function return domains fail before native execution. This is an abstract-domain safety check for the declared IR model, not a whole-program simulation proof or proof of the PHP frontend/emitter implementation.

`intdiv` and `%` preserve truncation toward zero and PHP's dividend-signed remainder. The actual PHP source runner and generated compatibility helpers preserve `DivisionByZeroError: Division by zero` and `DivisionByZeroError: Modulo by zero`, including preceding output. Any interval that can combine `PHP_INT_MIN` with divisor `-1` is conservatively excluded. In particular, exclusion of the remainder edge is a declared profile restriction rather than a claim that its actual native behavior is unknown in every PHP version.

Finite loops have literal integer start/stop, matching comparison and `++`/`--` direction, at most 128 iterations and at most 4096 expanded IR statements. The frontend unrolls their independently verified local arithmetic and preserves PHP's final counter value. The loop body cannot mutate its counter, nest/escape loops or return. Bounds cannot contain calls; this prevents eliminating a repeated condition's error or other behavior. Arbitrary while/for loops and resource-equivalent termination are not qualified.

Example source and independently specified contract:

```php
<?php
function Twice(int $x): int { return $x * 2; }
echo TWICE(-17), PHP_EOL;
```

```json
{
  "twice": {
    "parameters": {"x": {"type": "int", "min": -1000, "max": 1000}},
    "returns": {"type": "int", "min": -2000, "max": 2000}
  }
}
```

The original-intent acceptance for this example is independently `expected_stdout="-34\n"`, `expected_error=null`; the acceptance result is never read from the generated program to create its own oracle.

Run from the v4.7 source root with its native dependencies activated:

```sh
source /workspace/.onboarding/activate-usl.sh
python -m unittest tests.test_v47_php
python -m tools.qualify_semantic_php
```

The qualifier runs 25 independent source fixtures against both Python and JavaScript targets: 50 source/target comparisons and 100 fresh native executions, plus 24 invalid/unsupported-source checks and a tampered-IR overflow check. It records source/runtime/parser/helper identities and rejects a source change during the run. Ordinary tests additionally exercise declared-domain violations, counter state, unsupported host variables/builtin redefinition, reference-return refusal, Boolean function contracts, canonical JSON parameter-key order and changed IR semantics. Bounds bind to source parameter names rather than JSON insertion order. The expected results cover signed quotient/remainder, int64 boundaries, Boolean branches, positive/negative/zero loops, bounded functions, and actual error identity/partial output.

This work leaves PHP floating-point/overflow promotion, other scalar coercions, strings/arrays/objects, references/closures/modules, its standard library and extensions, general loops, ABI/callback/lifetime/concurrency behavior, whole-standard conformance, other platforms and OS sandboxing unqualified. A native-source parser, finite interval proof or these passing fixtures does not complete PHP's full semantics or the 606-language objective.
