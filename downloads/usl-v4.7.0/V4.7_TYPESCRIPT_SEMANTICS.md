# Typed TypeScript source translation profile

`usl.typescript.typed-bigint.v1` is a real TypeScript source frontend. It parses
the actual installed upstream tree-sitter TypeScript grammar, extracts source
annotations, runs the actual `tsc --strict` compiler, validates annotation erasure
against real ASTs, and lowers through the existing independently checked
`usl.semantic.typed-effects.v2` IR to Python or JavaScript.

There is no foreign-source execution envelope in the generated translation.
Native reference execution compiles the original TypeScript with `tsc` and runs
the compiler-produced JavaScript on Node. Generated target execution is separate.
Full TypeScript/ECMAScript conformance and universal semantic/intent proofs remain
unqualified.

## Supported source profile

Functions have ordinary required positional parameters and explicit source return
annotations. No external signature guesses are needed. Accepted annotations are
`bigint`, `boolean`, `string`, `bigint[]`, `boolean[]`, `string[]`, corresponding
`Array<T>` forms, and `void` for function returns. Scalar and nonempty-list local
bindings may be inferred; empty arrays require an actual source annotation.
Function/local annotations are independently checked against the lowered IR in
addition to the native TypeScript checker.

Supported execution includes typed functions, all-path returns, conditionals,
boolean short circuit, homogeneous lists, alias-preserving assignment and
parameter mutation, discarded `push`, string concatenation, strict equality,
BigInt arithmetic/comparisons, signed truncating division/remainder, `String`,
`BigInt(string_or_list.length)`, string/list `for...of`, and the existing canonical
BigInt `for` loop profile with literal bounds, unit steps and no body mutation of
the counter. `console.log` accepts at most one scalar. Functions precede ordinary
execution and may not capture global data or form recursive call cycles.

The runtime policy is ECMAScript: arbitrary-precision BigInt, UTF-16 string
length/ordering, Unicode code-point string iteration, array reference equality,
lowercase boolean output, and native `RangeError` on BigInt division by zero.
The existing target compatibility helpers preserve these differences in Python.
TypeScript Number/floating-point semantics are rejected rather than replaced
with integer semantics.

The observed host profile is Linux x86-64 with TypeScript compiler 7.0.2,
tree-sitter-language-pack 1.22.1 / tree-sitter 0.26.0, Node 24 and CPython 3.12.
The report records exact versions and executable/library/grammar hashes rather
than assuming the same version string denotes the same implementation.

## Structural erasure and source provenance

Erasure replaces only validated `type_annotation` AST byte spans with whitespace,
preserving original UTF-8 byte offsets and newline positions. Typed parameter
wrappers normalize to their actual runtime identifier nodes. A canonical runtime
AST comparison preserves operators, identifiers, literals, member names, order and
evaluation structure. Comments and semicolon punctuation do not contribute to
that runtime-shape identity. Literal strings containing text such as `: bigint`
are untouched.

The erased source is parsed by the actual JavaScript grammar. Its normalized
runtime AST must match the TypeScript runtime tree, and the compiler-produced
JavaScript must also match after accounting for the compiler-inserted strict
prologue. Unsupported casts, assertions, modules, type declarations or runtime
transformations never disappear because their spelling resembles a type.

IR functions, parameters, lexical bindings, loop variables, expressions and
statements retain original byte spans. Line and byte-column coordinates are
reconstructed from retained original UTF-8 bytes. The frontend avoids retaining
extension-backed Point objects; repeated translations and JSON serialization
remain valid after parser objects are released.

IR source hashes refer to the original typed source. Erased source, native
compiler output and translated target code have separate hashes. Parser grammar,
compiler executable, compiler/library closure, Node runtime and implementation
identities remain attached to the evidence.

## Native typecheck and artifact reuse

The actual native flags are:

```text
--strict --noEmitOnError --target ES2020 --module ES2020
--lib ES2020,DOM --newLine lf --pretty false
```

Compilation runs in a private directory with an empty `typeRoots` directory to
avoid implicit project/ambient package declarations. The DOM library supplies the
`console` type declaration; actual qualified execution uses Node's scalar console
behavior. Imports/exports and other module behavior are unsupported. TypeScript
7.0.2 rejects the obsolete `--module none` option, so it is not used.

Compiler suppression/control comments (`@ts-ignore`, `@ts-nocheck`,
`@ts-expect-error`, other `@ts-` pragmas) and triple-slash reference directives are
rejected. They cannot weaken a required native typecheck, including when a pragma
appears inside an annotation. Unsupported `any`, `unknown`, unions, readonly
ownership, type aliases and generic polymorphism also fail explicitly.

Pure compilation artifacts can be reused within a process only when the complete
source/compiler/library/Node/platform/configuration identity matches. The cache
records whether the compiler actually executed on the current call. It never
replaces native program execution with previously observed output. A changed
source or relevant compiler/dependency identity creates a different artifact key.
Compiler execution has a deadline and bounded diagnostics; program execution
inherits the existing CPU/wall/output/process-group controls. Neither runner is
an operating-system filesystem/network security sandbox.

## APIs and integration

```python
from usl_systems.semantic_typescript import (
    TypeScriptFrontend, translate_typescript,
    compile_native_typescript, differential_verify_typescript,
)

ir = TypeScriptFrontend(source).lower()
translated = translate_typescript(source, "python")
compiled = compile_native_typescript(source)
result = differential_verify_typescript(
    source, "python",
    intent={"intent": "Return the required label",
            "expected_stdout": "accepted\n",
            "expected_error": None},
)
```

For shared compiler integration, dispatch TypeScript source to
`TypeScriptFrontend(source).lower()`, use its IR profile and original source hash,
then use the existing Python/JavaScript emitters. The qualified targets are Python
and JavaScript; other routes need separate qualification.

For a shared native runner, `compile_native_typescript` returns native strict
compiler evidence and executable `code`. Execute that code freshly on Node and
retain the original source/compiler hashes. The existing exception harness wraps
source inside `try`; use an IIFE around compiler output so its `"use strict"`
prologue remains a function directive rather than becoming an ordinary block
expression. The standalone verifier already preserves that strictness.

## Evidence and remaining work

Run:

```sh
python -m tools.qualify_semantic_typescript
python -m unittest tests.test_v47_typescript
```

The recorded suite covers 28 distinct source fixtures, including 10 randomized
heldouts with an independent mathematical sum oracle. Both targets are tested:
56 source/target differential cases and independent intent acceptances, with 112
actual native program executions. It also includes 30 unsupported/invalid-source
admission checks, including six observed native TypeScript typecheck rejections.
The regression module contains 12 tests.

Source-target agreement and satisfying an independently supplied intent contract
are separate results. Missing or incorrect intent never yields an intent-pass
claim. Tests cover effects/output ordering, errors, aliases, scope-specific empty
arrays, UTF-16 differences, BigInt precision, loop boundaries, source spans and
native strict type errors. Reports identify what was executed versus compiled or
reused. Qualification status remains `subset_behavior_observed`.

Whole standards, Number/IEEE-754, objects/classes/prototypes, closures, modules,
arbitrary library APIs, advanced generics/conditional/mapped/union types,
assertions/satisfies, async/concurrency, native ABI/lifetimes, termination/resource
equivalence, authoritative complete conformance and formal source-target
simulation remain outstanding. A successful strict typecheck and finite native
suite do not prove every arbitrary TypeScript program or the entity's complete
original objective. No all-606 completion or full-specification claim is produced.
